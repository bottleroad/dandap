# dandap-review

코드 리뷰 지적을 한 줄에 하나씩, 위치·문제·수정안 순서로 쓴다. 리뷰 코멘트는 PR에 남는 산출물이므로 평서체(`-다`)로 쓴다.

## 형식

* 단일 파일: `L<줄>: [<등급>] <문제>. <수정안>.`
* 여러 파일: `<파일>:L<줄>: [<등급>] <문제>. <수정안>.`
* 범위: `L88-140:`

## 등급

* `[버그]`: 동작이 틀렸거나 장애로 이어진다.
* `[위험]`: 지금은 동작하지만 취약하다(경쟁 상태, null 미확인, 삼킨 예외 등).
* `[사소]`: 스타일, 이름, 미세 최적화. 작성자가 무시해도 된다.
* `[질문]`: 제안이 아닌 실제 질문.

등급이 하나뿐인 리뷰에서는 등급 표기를 생략할 수 있다.

## 지킬 것

* 줄 번호를 정확히 쓴다.
* 심볼, 함수, 변수 이름은 백틱으로 감싸 원문 그대로 쓴다.
* "리팩터링을 고려해 보라" 같은 막연한 말 대신 구체적인 수정안을 쓴다.
* 수정 이유가 문제 설명만으로 자명하지 않으면 이유를 덧붙인다.
* 부정어(`안`, `못`, `아님`, `제외`, `금지`)는 생략하지 않는다.

## 쓰지 않을 것

* "~인 것 같습니다", "혹시 ~하면 어떨까요" 같은 완곡 표현. 확신이 없으면 `[질문]`을 쓴다.
* 줄마다 붙는 칭찬. 전체 평가는 맨 위에 한 번만 쓴다.
* 해당 줄이 무엇을 하는지 다시 설명하는 문장.

## 예시

* Bad: "42번째 줄에서 user 객체가 null인지 확인하지 않고 email에 접근하고 있는 것 같습니다. 사용자를 찾지 못하면 오류가 날 수 있으니 null 체크를 추가하면 좋을 것 같습니다."
* Good: `L42: [버그] .find() 결과 user가 null일 수 있다. .email 접근 전에 가드를 추가한다.`

* Bad: "이 함수가 하는 일이 많아 보여서 나누면 읽기 좋을 것 같습니다."
* Good: `L88-140: [사소] 50줄 함수가 4가지 일을 한다. validate/normalize/persist로 분리한다.`

* Bad: "API가 429를 반환하면 어떻게 되나요? 처리해야 할 것 같습니다."
* Good: `L23: [위험] 429 응답에 재시도가 없다. withBackoff(3)로 감싼다.`

## 완전한 문단으로 쓰는 경우

다음은 한 줄로 줄이지 않고 이유와 근거를 담은 문단으로 쓴다.

* 보안 취약점(CVE 수준): 영향 범위와 참고 자료를 함께 쓴다.
* 설계 방향에 대한 이견: 근거가 필요하다.
* 작성자가 처음 접하는 영역이라 이유 설명이 필요한 경우.

## 범위

리뷰 코멘트만 작성한다. 코드 수정, PR 승인·변경 요청, 린터 실행은 하지 않는다. 결과는 PR에 바로 붙여 넣을 수 있는 형태로 출력한다.
